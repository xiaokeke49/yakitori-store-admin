# 冰箱账号运营：安装与使用说明

## 现在怎么用

本 Skill 负责同行研究、拍摄策划与示意图、实拍验收、发布预览、后台读取和复盘。第一版小红书优先，使用 Markdown 台账，不建数据库，不自动创建定时任务。

| 你说什么 | 会得到什么 |
|---|---|
| `$fridge-account 研究20个冰箱拍得好的烧鸟账号` | 严格筛选的同行记录、原帖链接、参考素材和可复制方法；不足20个会显示缺口 |
| `$fridge-account 根据同行给明天的拍摄任务` | 机位、光线、布置、动作、替代拍法及验收标准 |
| `$fridge-account 生成拍摄示意图` | 明显标注“拍摄示意·非现场实拍”的图和对应拍摄任务 |
| `$fridge-account 用右侧浏览器读取后台并复盘` | 真实可见数据、缺失项、变化与下一轮改进；登录/读取失败如实记录 |
| `$fridge-account 看看这些实拍是否达到示意要求` | 原图对照、可用图与补拍任务 |
| `$fridge-account 制作发布预览，先不发布` | 核实素材来源与真实性的图片、文案和发布核对项 |

示意可以与现状不同，供人布置拍摄；同行素材只供研究；两者都不能混入自家发布候选。规则详见 [SKILL.md](SKILL.md)。

## 安装与更新

适用于本项目的 macOS + Codex 环境。需要先安装 [Codex](https://developers.openai.com/codex/app/)，并把私有仓库 [yakitori-store-admin](https://github.com/xiaokeke49/yakitori-store-admin) 克隆或拉取到本机。协作者需要仓库访问权限。该 Skill 的安装本身不需要 Python、Node、API Key 或 `pip install`。

1. 在 Codex 中打开本仓库。
2. 在仓库根目录打开终端，执行下方命令。第一条检查应显示 `SKILL.md` 路径；若不存在，先检查当前位置和仓库版本。
3. 安装后，在下一轮对话调用 `$fridge-account`。

```sh
ls "09_系统与自动化/skills/fridge-account/SKILL.md"
mkdir -p "${CODEX_HOME:-$HOME/.codex}/skills"
ln -s "$PWD/09_系统与自动化/skills/fridge-account" "${CODEX_HOME:-$HOME/.codex}/skills/fridge-account"
```

目录关系如下：

```text
仓库/09_系统与自动化/skills/fridge-account/SKILL.md  ← 唯一正式文件
本机 ~/.codex/skills/fridge-account/               → 指向仓库目录的软链接
```

如果设置了 `CODEX_HOME`，本机安装位置相应为其下的 `skills/fridge-account`。每位协作者各自在自己的电脑安装一次；软链接不会随 Git 分享到其他电脑。

第一条应显示当前仓库中的技能目录，第二条应显示“Skill 文件可读取”。接着在 Codex 下一轮对话发送：

```text

## 第一次使用前准备什么

| 资料或条件 | 如何提供 | 缺少时怎么处理 |
|---|---|---|
| 原始照片 | 上传附件或给出本机文件夹完整路径 | 没有素材无法制作真实图文 |
| 拍摄日期 | 标注当天或历史素材；不同日期分开说明 | 无法确认时按历史素材处理 |
| 商品信息 | 已知名称、价格依据、库存和当天经营例外 | 不猜测，可先做不含价格的预览 |
| 历史发布记录 | 提供现有记录或已发布作品链接 | 标注去重未完全核实，实际发布前补齐 |
| 平台操作条件 | 实际发布前由你完成所需登录，并核对账号和地点 | 可以先做预览，无法核对时不发布 |

不要把密码、验证码、Cookie 或 Token 写进仓库或聊天。账号和门店的固定口径查看 Skill 中的“固定经营资料”，有变化直接说明。

素材文件夹：[本机照片文件夹完整路径]

库存及当天经营例外：[已确认信息或未知]
历史发布记录：[记录路径/作品链接/暂无记录]
不能出现的内容：[没有或具体说明]
希望发布时间：[时间或按 Skill 默认]
```

| 场景 | 可以直接这样说 |
|---|---|
| 只检查素材 | `$fridge-account 检查这批照片是否够用、是否可能重复，先不修图。` |
| 调整预览 | `$fridge-account 把刚才那版文案改得更像老板日常，给我新版本预览。` |
| 发布已确认版本 | `$fridge-account 确认发布小红书预览 [日期/版本]，先核对账号和地点。` |

只确认图片不等于确认整篇发布。图片、图序、文案、音乐、发布时间、账号或地点变化后，要重新提供完整预览并确认版本。若当前没有平台操作工具，Codex 应交付可手动上传的文件并说明未发布；不会因为回复“确认发布”就假定发布成功。

| 内容 | 相对于仓库根目录的位置 |

| 成功发布记录 | `06_公域运营/产品展示冰箱/小红书发布记录.md`，首次实际成功发布时建立 |

同日多版使用版本号；已确认或已发布的版本不覆盖。发布记录应包含时间、作品链接、版本、原图路径与 SHA-256 等信息。上述产物路径是约定，不表示文件已经生成。

在 GitHub Desktop 中拉取仓库最新内容即可更新规则；软链接不需要重复安装。自己修改规则时只编辑仓库中的 `SKILL.md`，不要另存本机副本。遇到 Git 冲突先解决冲突，再继续使用。

| 问题 | 处理方法 |

| 安装提示 `File exists` | 先运行 `readlink`。如果已经指向本仓库且文件可读取，就是已安装；若是其他目录或普通文件，先检查并备份，不要强制覆盖 |

## 记录工具：无需数据库

脚本只处理本地记录，不会登录、爬取或发送内容。正常使用时让 Codex 读取页面后调用；下列命令供维护者验证。Python 3 标准库即可，无需安装额外依赖。

在仓库根目录运行：

```sh
python3 09_系统与自动化/skills/fridge-account/scripts/records.py init
python3 09_系统与自动化/skills/fridge-account/scripts/records.py status
python3 09_系统与自动化/skills/fridge-account/scripts/records.py diagnose
```

`init` 仅提示按需记录，不创建任何空表。`status` 显示合格同行账号数和数据缺口。`diagnose` 仅输出数值检查草稿，不生成增长原因结论。最终分析由 Codex 对照内容和同发布时长补充到项目 README。

### 导入真实记录

先将本次读到的字段整理成一个临时 JSON 对象，再调用 `ingest 类型 文件路径`。JSON 仅作为输入，Markdown 是正式来源。使用仓库外临时目录，用完清理；测试数据不导入正式台账。

| 类型 | 必填字段（中文键） | 正式文件 |
|---|---|---|
| metrics | 账号、作品、采集时间、统计区间、指标、口径、值、单位、证据 | 后台数据.md |
| peers | 账号、作品、观察时间、平台评论、顾客评论、正向兴趣评论、完整核实、冰箱相关、证据、对照作品 | 同行研究.md（有有效案例才建立） |
| assets | 文件、用途、版本、验收、说明；发布候选另需原图SHA256 | Skill内部 data/素材登记.md |
| published | 时间、链接、版本、成片SHA256、原图SHA256、成功证据 | 小红书发布记录.md |

`metrics` 的值使用数字或 `null`（缺失）；时间必须含时区；口径为“累计/区间/时点”。不要把“1万+”猜成精确10000。比例单位用 `%`，不与次数混算。证据填写原页面链接及本地证据位置。

`peers` 的“完整核实/冰箱相关”为“是/否/未知”，计数可填 `null`。结论由脚本计算；计数至少20、正向兴趣评论占有效顾客评论至少30%（分类去重，详见Skill）、完整核实且有证据与对照作品才算合格。脚本不能代替人核实证据真实性。分析与拍摄方法直接写在同行主记录的表格区，不写进指标字段。

`assets` 的用途为“自家原图/策划示意/同行参考/发布候选”，验收为“待核实/通过”。文件可使用相对选题目录的路径；脚本计算成片 SHA-256，原图多个 SHA-256 用英文逗号连接。原图与发布候选必须分别登记，通过视觉检查后再录入“通过”。图发生变化必须登记新文件与版本。

```sh
python3 09_系统与自动化/skills/fridge-account/scripts/records.py ingest metrics "本次指标.json"
python3 09_系统与自动化/skills/fridge-account/scripts/records.py check-package "制作内容/日期/成片.jpg"
```

`check-package` 检查文件摘要、用途、原图来源与成功发布去重；它不会判断图像是否真实，也不提供发布授权。发布成功后用 `published` 记录；其原图摘要必须与素材台账一致。

同一指标的账号、作品、时间、区间、指标、口径相同且内容一致时跳过；内容不同报冲突，不能覆盖。同行按账号/作品/观察时间去重；素材按文件摘要去重。单个 Codex 串行维护台账，禁止多个写入者同时运行；手动补充放在 `records:start/end` 标记之外。

### 后台与素材入口

优先使用用户指定的右侧内置浏览器，不能因读取超时就断言未登录。原图从 Uploader 查询/拉取，使用现有原生 OSS 工具；同行参考作为独立分类保留出处。网络或页面不可用时可继续策划，但日报必须显示缺失，不把假设写成真实复盘。

### 开发验收

```sh

```

测试在临时目录中运行，覆盖去重、缺失与零、负向修订、同行门槛、示意改名拦截、发布来源与去重，不会污染真实台账。

老板已删除“同行参考”层级，不得自动重建。用户提供的已选参考在仓库顶层 `素材库/用户提供/`；当前拍法集中在选题README。

## 单图制作 Live Photo

**本账号默认：实拍 → 选图排序 → 轻修 → 生成Live → 动态验收 → 发布预览 → 确认发布。** 你提交实拍并要求制作内容后，Codex在选图完成后自动执行Live制作，不需要你再单独下指令。只有选中的图会制作，整库图片不会批量转换。

直接对Codex说：**“用fridge-account把这张实拍做成Live，先给我预览。”** 附图片或提供原图路径即可。当前实现使用Mac本地Apple框架，无需生视频API；需要macOS及可用的Swift编译器。

在仓库根目录运行（替换输入原图；省略输出参数即可自动进入顶层素材库的Live图类别）：

```sh
python3 09_系统与自动化/skills/fridge-account/scripts/make_live.py \
  "素材库/烧烤食材展示/图片/WechatIMG37.jpg"
```

| 文件 | 怎么用 |
|---|---|
| Fridge_Live.JPG ＋ Fridge_Live.mov | 一组配对资源，必须一起保留，不是两个独立发布文件 |
| 推近效果预览.mp4 | 先看动态效果；单独发送它只会是视频 |
| 验收/ | 程序验证报告与首尾检查图，技术检查用 |

效果：3秒竖幅轻微推近、模拟少量手持位移，食物与湖的相对结构不生成变化。普通静态照片也能做，但不能恢复拍照前后的真实动作。默认中心裁切，主体靠边或横图需要先选图验收。

程序已包含配对标识、关键照片时间及PhotoKit文件识别验证。老板实测直接拖入Mac照片会拆成两个项目；现在使用下方专用导入器将配对资源写成一个Live项目。文件配对验证不等于图库导入验证；小红书手机端仍需确认LIVE标识及播放效果。尚未承诺Mac小红书网页端支持此配对上传。

遇到“输出目录已存在”换v2/v3，不覆盖旧版本；编译器缺失先处理Mac开发工具；配对验证失败不会交付成品目录。制作不自动导入相册、不上传、不发布、不把原图登记为已发布。

## 导入Mac照片为一个Live项目

首次在Mac上构建（在仓库根目录执行；输出路径必须不存在，已构建可直接使用）：

```bash
python3 09_系统与自动化/skills/fridge-account/scripts/build_live_importer.py \
  "output/冰箱实况导入器.app"
```

1. 双击构建出的“冰箱实况导入器.app”。它是本地构建并临时签名的Mac程序，首次编译需要Xcode命令行工具。
2. 选择包含 **Fridge_Live.JPG 和 Fridge_Live.mov** 的同一个成品文件夹，不选择MP4预览或ZIP。
3. 核对弹窗，点击“导入一张实况照片”；在系统弹窗允许照片读写权限。读权限用于回读新项目类型及去重，程序不遍历其他照片。
4. 程序只有在写入后回读到 `.photoLive` 时才显示“已导入一张实况照片”。打开Mac照片App的“媒体类型→实况照片”，检查LIVE及动态播放。
5. 从照片App分享这张实况照片，通过隔空投送传到iPhone；或等待两端已开启的同账号iCloud照片同步。手机相册先验证LIVE且长按可播放，再在小红书上传预览里验证。不要只传JPG或MP4。

程序不会删除先前分别导入的图片/视频，不会上传小红书。不能将生成动画称为现场实拍动态。

| 提示/现象 | 处理 |
|---|---|
| 缺少资源或标识不一致 | 检查JPG/MOV来自同一版本，不能混搭或只导入预览视频 |
| 没有照片权限 | 系统设置→隐私与安全性→照片，允许冰箱实况导入器后重试 |
| 已导入，未重复添加 | 到媒体类型→实况照片寻找已导入项目，不再添加 |
| 写入完成但回读未确认、或已有回执但项目不可读 | 先检查当前系统照片图库；程序保留回执并停止，避免盲目重复导入 |
| Mac可播放、手机或小红书变静态 | 检查传输是否保留Live；不能将Mac验证当作平台验证 |

只检查文件而不导入、不请求图库权限：

```bash
"output/冰箱实况导入器.app/Contents/MacOS/LivePhotoImporter" \
  --check "素材库/Live图/日期/主题_Live_v1"
```

本轮已验证：本机编译和签名、有效配对通过、缺失文件与跨版本错误配对被拒绝。2026-09-09已从图库回读确认本组资源为photoLive，并在Mac照片App的实况照片分类看到展示柜图片及“实况”标识；重复运行未重复添加。跨设备传输与小红书识别尚未验证。

已明确授权导入且已知目录时，可用 `open -n "output/冰箱实况导入器.app" --args --import "成品文件夹绝对路径"` 跳过选目录和程序确认弹窗；系统照片权限仍必须获得授权。成功后成品目录写入 `导入结果.json`，以其中 `photoLive: true` 和图库回读作为验证依据。早期进程曾返回权限错误；重启后已确认图库存在对应实况项目，未重复添加。


## Live图自动入素材库

默认路径：`素材库/Live图/生成日期/原图名_原图摘要前12位_v1/`。这是生成日期，不冒充原始拍摄日期。每组保留配对JPG、MOV、MP4预览、`素材信息.json`与验收文件；来源路径、SHA-256、Live配对ID、资源摘要和待验收状态自动记录。JPG/MOV不能拆开改名或只留一个；MP4不是Live替代品。

相同原图当天重复执行会拒绝覆盖，直接使用现有版本或明确指定素材库内v2目录。单图生成完成即入库，但不意味着已通过目视验收或已发布。原实拍保持原分类只读，发布预览引用本目录成品，不另存第二个正式副本。现有展示柜样例已迁入`素材库/Live图/2026-09-09/展示柜_Live_v1/`。

OSS已加入同名分类；本地入库不等于云端已上传。需要云同步时用uploader按整组目录扫描、确认上传范围，JPG/MOV保持同批、同分类和相对路径。预览MP4、验收检查图不是独立Live成品；当前通用上传器不上传JSON，不能声称云端已保存来源台账。来源信息以本地素材信息为准。


## 图片数量与背景音乐

不固定发布3张或其他张数。每篇按主题和素材质量选图，预览明确实际张数及逐页顺序；拍摄备选数量和拼图内小图数量不是发布页数。

每次预览同时包含对应平台的音乐建议、歌曲/版本、曲库条目、核实时间、适配理由与待确认项。第一版小红书优先，抖音另行核实。Live生成文件当前无声，音乐在平台编辑页选择；不能称已嵌入Live。无法核实曲库时标记待核实；换歌后重新确认整包。详细规则见[Skill背景音乐](SKILL.md#背景音乐)。
