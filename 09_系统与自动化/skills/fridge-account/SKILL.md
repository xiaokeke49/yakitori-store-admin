# 冰箱账号运营

## 适用范围与项目位置

仅服务游味烧鸟的冰箱账号；已确认的小红书昵称为“游味烧鸟｜长沙湖边烧鸟”。本 Skill 是该账号小红书流程的唯一正式来源，不是其他账号的通用内容模板。

业务目录为本仓库的 `06_公域运营/产品展示冰箱/`；下文“当前项目”均指这个选题目录，发布预览和记录保存在其中，不放进 Skill 安装目录。安装、验证、使用示例、更新和卸载方法见[使用说明](使用说明.md)。

Skill 提供操作规则，不自带平台登录、自动发布程序或定时任务。实际发布需要当前环境具备可用的平台操作工具；工具不可用时交付预览并说明发布尚未完成。

## 内容范围

“冰箱账号”是账号名称，不是只拍冰箱的限制。内容覆盖冰箱陈列与选串、炭火烤制、出炉上桌、满桌菜品、湖边用餐、晚霞与真实营业日常。每条选择一个主旨，可用“选串—烤制—上桌—湖边用餐”串联，但不强制每篇出现全部场景。老板已确认当前无法满足满桌菜品拍摄：仅保留为同行参考，不安排本轮实拍，改用真实单盘、少量串品与出炉动作。以后条件具备再启用。满桌菜品必须来自实际出品，烤制画面按真实操作拍摄。

同行参考库同时收录这些方向的优秀案例。它们可作为拍摄参考，不必满足冰箱研究门槛；原定20个冰箱相关合格账号仍按原条件单独统计，不将普通参考混入完成数量。

## 平台范围

名称按冰箱账号命名，不绑定单个平台。当前已定义的制作与发布流程适用于小红书；后续在同一 Skill 中扩展抖音流程与自动发布能力。抖音账号身份、平台规则和自动发布工具尚待配置，不直接套用小红书的账号、地点或发布时间。

## 同行研究与参考素材

目标是至少 20 个不同的小红书烧鸟账号：每个账号至少一条冰箱相关作品平台评论数至少 20，且完整核实、剔除作者及店主回复/重复记录/无关或无法判断内容后的有效顾客评论中，正向兴趣评论占比至少30%。正向兴趣包含问位置、问价格、想吃/想去/预约意向、正面口味或菜品评价；分别分类，同一条只计一次，不叠加多标签。负面和褒贬混合反馈保留分母，不能为凑比例剔除；纯表情或含义不明不擅自判正向。不同顾客的相同短句不是重复记录。问址、问价、意向、评价分别保留小计，不能将全部正向评价称为到店咨询。

按老板要求，从顾客会用的“烧鸟”站内搜索开始，全国取样、优先长沙；不以“烧鸟 冰箱”作为主搜索词。优先在搜索筛选中按评论排序找咨询候选，再按点赞排序补充画面参考；记录搜索词、排序方式和观察时间，页面未核实时不猜排序。进入作品后再判断陈列、烤制、出品和用餐场景，排除冷柜销售、设备转让和教程等非用餐咨询作品。先查看作品相关性与计数，再加载完整评论和回复并分类；记录平台计数与实读数量的差异。无法完整读取、计数模糊、来源打不开均标记候选，不计入 20 个。每个账号至少对照一条普通表现作品。不能用点赞替代评论、热门评论替代全体或伪造 20 个账号。

每个案例在同行主记录中集中维护账号/作品链接、观察日期、统计证据、完整性、有效评论分母、正向兴趣去重分子与分类小计、对照作品、画面与标题方法、我们如何复现及不确定因素。区分“观察事实”和“成功原因假设”，不能从公开数据断言对方投放或成交。

每个重点案例必须实际查看并保存图片，不能只记录互动数字或用文案猜画面。优先按原帖顺序保存可获取的整组图片；逐张记录构图、主体占比、机位、明暗与色彩、食物纹理、陈列、人物动作、背景及顺序作用。每项区分画面事实、效果假设和本店试拍方法；设备、焦距、灯位未经证实不当作事实。原文件不覆盖，记录原帖、图序、采集时间、SHA-256及用途“同行参考”。失败标明应有/已存数量与缺图，不能把链接或评论表当作图片采集完成。拆解集中放同行README，拍摄任务据此落到可操作机位、布置、验收与替代方案。

参考图、局部截图和合法可获取的原素材存入 仓库顶层素材库中经老板确认的现有分类；不再创建“同行参考”目录，以主记录索引，不复制整篇笔记或顾客身份资料。下载失败时保留原帖链接与状态。Uploader 新分类“同行参考”只用于学习资料，旧 hash 不重新分类，上传遵守 uploader 的预览与确认流程。同行照片不进入自家发布候选，也不冒充自家生图的商品/现场依据。

## Computer Use 后台采集与诊断

先寻找用户指定的右侧浏览器，不擅自更换登录环境。核对本账号主页 ID `6614a053000000000d026f9b` 及昵称，再进入创作者中心。昵称标点差异可人工核对，不只凭相似名字。主页公开数不能冒充后台数据。

读取可见字段与统计区间后，把账号、作品、采集时间（含时区）、区间、指标、累计/区间/时点口径、数值、单位、证据写入后台数据表。未显示记“缺失”；0 仅用于明确显示为零。后台汇总私信优先，不读取私人聊天正文。保存证据时不包含登录凭据或无关顾客隐私。

复盘必须包含变化、证据、可能原因和不确定性、一个优先改进项、补拍任务、下次检查时间。对同类作品比较相同发布时长，记录内容形式和发布日期；累计值只有同一作品同一指标口径才可作差，下降标记平台修订待核对，不改成零。百分比不作数量增量。分母缺失或为零时不计算比例。

曝光弱、点击弱、互动弱、咨询弱分别列为诊断线索，必须由对应可见数据支持；无曝光指标就不能判断点击率。数据不足时输出“建立基线/继续观察”，不编造原因或行业阈值。第一版不采集到店记录，不声称实际成交。

先手动跑通一次，不创建定时任务。每次页面超时最多换一种合法读取方式再重试一次；登录失效、验证码或重复超时记录失败并继续独立工作。缺失不是零，也不算成功采集。以后确定运行时间后再创建定时任务。

## 策划示意与素材合成

先使用 Uploader 检索、拉取自家素材并查看原图；已有本地副本可复用，远程不可用时如实标注来源时间。图像生成使用已安装 imagegen 的内置工具，参考图路径明确，原图只读。

| 用途 | 可以做什么 | 进入发布包条件 |
|---|---|---|
| 策划示意 | 生成新陈列、机位、灯光和动作，可与现状不同 | 永不直接进入发布包；另做实拍或核实后的发布候选 |
| 发布候选 | 实拍或经过逐项真实性核实的自家素材合成 | 来源可追溯、检查通过且当前版本获得确认 |
| 同行参考 | 保存其他账号优秀画面与方法 | 不进入自家发布包 |

每张示意图必须明显标注“拍摄示意·非现场实拍”，并配套编号对应的拍摄任务，说明已有条件、创意假设、如何实现与替代拍法。不会实现的空间关系必须说明；不得暗示冰箱已在湖边。示意存 `策划示意/<日期>/`；人员实拍按原位置保留，制作候选存 `制作内容/<日期>/`。

在Skill内部素材登记记录文件 SHA-256、用途、参考原图 SHA-256、版本、验收状态；同一文件不能从示意偷偷改成候选。参考示意可复用素材，发布候选继续追踪原始 hash，不以裁切/改名/生图绕过去重。图中标识丢失须重做；合成图实际发布前核对平台生成内容标识要求。

## 已发布照片去重

已经成功发布过的原始照片不得再次使用；对同一原图进行裁切、调色、压缩、改名或导出后仍视为同一张照片。只生成过预览但没有成功发布的照片不算已使用。

选图前：

- 检查项目现有发布记录、历史发布包和已发布素材清单。
- 优先使用原图文件名、原始路径和 SHA-256 摘要识别完全相同的照片。
- 对改名、压缩或裁切版本进行画面比对；疑似属于已发布照片时不选用，并列入待确认项。
- 现有记录不足以证明照片未使用时，如实标记“去重状态未完全核实”，不得声称一定没有重复。

首次实际发布时，如项目没有统一记录文件，则建立 `小红书发布记录.md`（只维护发布结果，数据分析引用链接，不复制历史）。每次发布成功后记录原图文件名、原始路径、SHA-256、成片文件名、发布时间和发布链接。发布未成功时不把照片标记为已使用。

## 策划与选图实验

发布图片数量不固定为3张、5张或18张。按本篇主题、素材质量、各页新增信息及平台实际支持数量确定，并在完整预览中列出实际张数与顺序；教学中的备选原图数量、拼图格数不等于发布页数。

先输出拍摄任务，再选图；每轮只优先改变一个因素。冰箱首图、满桌菜品首图、烤制动作首图、湖边用餐首图、取串动作首图都是可测试方案，不再强制前三张冰箱、固定总张数或永久固定发布时间。比较同类作品相同发布时长的结果，记录实验变量与其他变化，不能把不同流量规模直接归因于首图。

拍摄表必须有：编号、参考案例或“待验证假设”、表达目的、机位与镜头方向、光线、人物动作、道具与布置、现有条件、待确认条件、替代拍法、验收标准、负责人、下一步。未知负责人标记“待老板确认”。

可试验柜内陈列吸引力、满桌菜品的丰富感、炭火烤制与出炉动作、湖边烧鸟酒饮用餐场景、傍晚到亮灯的氛围。酒饮必须核对实际在售商品；湖景构成优势是待验证假设，不是效果保证。

## 图片编辑与真实感

允许以自家实拍为参考做AI编辑、合成、光线调整、天空处理及陈列策划，不再将合成方式一刀切禁止。先明确用途：策划示意可以表达新的布置与效果并标注非实拍；发布候选需要核对商品和门店事实，不能仅凭“看起来真实”认定可发布。历史照片可加工，但不冒充当天照片；生成顾客不能当真实客流证据，改变空间的创意不能当现有门店实况。

当前用已可调用的imagegen制作；外部GitHub项目是方法与候选工具，未经安装实测不称已接入。检索结论集中见同层使用说明，不另建素材研究垃圾目录。

操作：先查看参考原图，明确每张参考负责商品、环境还是构图；写清本次改变项与保持项，避免一次重生成全部内容。保持自然纹理、合理透视、统一光向和接触阴影；放大检查竹签是否断裂/粘连、串品形态、玻璃反射、托盘边缘、手部与文字。修复清晰度也可能新造细节，不能将其当作真实商品细节证据。

逐张对照原图并记录实际改动；合成后的品种、份量、配料、包装与门店景观需与实际可提供条件一致，无法核实则留作示意或重做。发布预览说明AI处理范围并核对平台标识要求，老板确认当前版本后才发布。

顺序为选图 → 必要编辑/合成 → 静态验收 → 生成Live → 动态验收 → 发布预览。原图保持只读，修改版另存，不能通过合成或Live绕过已发布原图去重。

## 文案

- 小红书优先。主动拆解高赞、高评论案例的标题、开头、卖点顺序和评论引导，结合本店菜品与湖景改写。跨平台也可以借鉴，但要匹配当前图片和平台表达习惯，不照搬原文或虚构经历、评价、销量。
- 选参考文案时，同时查看评论内容，优先学习引发问位置、问价格、想吃或想去等有效兴趣的表达；不能仅凭点赞、评论总量认定文案适合本店，也不把互动效果全部归因于文案。
- 可突出真实照片支持的湖景、晚霞、舒适环境和晚餐氛围。
- “当天现串现用”属于用户确认的固定营业事实，可以用于文案；若当天经营情况有例外则停用。
- “食材新鲜”仍需照片或当次资料支持，不能仅凭“当天现串现用”推断食材的新鲜程度。
- 历史照片使用不带具体日期的常青表达，不能写“今天刚上柜”“今天的晚霞”“今晚只剩这些”等时效性陈述。
- 商品、价格、库存或门店信息不清楚时不得猜测；未确认价格时写“价格可私信了解”。
- 不虚构销量、排队、顾客评价、限量、获奖或必然获得流量等事实。
- 标题自然、具体，正文包含真实看点、到店场景和适度行动引导，话题优先长沙同城、湖边用餐、烧鸟和晚餐场景。
- 标题、正文和话题标签中不加入高德地图、导航方式、门牌号、POI 核对过程等发布地点字段之外的信息；用户当次明确要求时除外。

## 背景音乐

- 每次按目标平台当时可用的正版曲库推荐音乐；第一版先核实小红书，要求抖音时另查抖音曲库，不把跨平台可用性当成同一件事。
- 音乐与当篇画面匹配，优先湖边、烟火气、轻松晚餐和真实营业氛围；不为追热点强配情绪冲突的歌曲。
- 预览列明歌曲名、歌手/版本、平台曲库入口或可追溯条目、核实时间及适配理由。核对当前账号与发布用途可用性，不能仅凭搜索到歌曲认定可用；无法访问曲库时明确标记待核实，不编造已可用的推荐。
- 不从不明来源下载音乐，不把一个平台下载的音乐直接搬到另一个平台。当前Live脚本输出无声资源，背景音乐在目标平台发布编辑页选择，不因此承诺已嵌入Live。
- 发布前再次确认选定歌曲仍可用；不可用时在同平台推荐同类氛围音乐，重新交付完整预览并获得确认，不能擅自换歌。
- 图片、文案、音乐和发布时间一起交付。仅确认图片或音乐不代表整包授权；用户当次明确选择无配乐时，把无配乐写入整包预览。

## 发布地点

每次图文发布都必须把发布地点设置为门店 POI“游味烧鸟”，不得省略地点或用“后湖”等泛化地点代替。

- 在小红书的“添加地点”中搜索“游味烧鸟”。
- 选择前同时核对门店名称、城市为长沙，以及后湖或岳麓区的地理信息，不能只凭同名结果选择。
- 小红书地点结果不明确、出现多个同名地点或没有结果时必须停止，请用户确认具体条目；不得猜选附近地点。
- 将最终选中的地点名称和核对依据放入发布预览；地点发生变化时必须重新让用户确认。

## 确认与发布

生成预览不等于获得发布授权。只有用户针对当前版本明确回复“确认发布”后，才能操作发布；只确认某一项不视为整包发布授权；修改图片、图序、文案、音乐、发布时间、发布地点或账号后，重新提供完整预览并确认。

发布前核对：

- 图片数量、顺序与本次确认的逐页清单一致，无固定2至3张限制
- 图片、商品和文案相互匹配
- 音乐与确认版本一致，已在对应平台再次核实可用性；无配乐须为本次明确选择
- 本批照片没有在成功发布记录中使用过
- 历史照片没有冒充当天素材
- 发布地点已设置为经核对的“游味烧鸟”门店 POI
- 门店信息准确
- 当前预览版本已获明确确认

任一项无法确认时停止发布并说明缺失信息。严禁在 Skill 或项目文档中保存密码、验证码、Cookie、会话令牌等登录凭据。

发布后记录平台、发布时间、发布链接、使用素材、实际使用音乐（歌曲/版本/平台条目，或无配乐）和发布包版本，避免重复发布。若页面没有显示成功结果，不得声称已经发布。

## 精简交付

只为真实成果建文件，不预建后台空表、快照目录或失败日志。素材统一归仓库顶层素材库，选题内只放策划、制作与发布成果。参考图片必须有明确可学习点和本店拍法；下载成功或评论达标不能代替视觉筛选。老板否定的参考退出正式推荐，不继续用其支撑教学。无效候选与临时文件按授权清理，不用仓库内归档持续堆积。

## 选图后的默认制作顺序

老板已确认：本账号默认按“人员实拍 → 查看全部原图 → 去重、选图与排序 → 必要轻修 → 将选定照片制作为Live Photo → 逐张动态验收 → 发布预览 → 当前版本确认后发布”执行。选图完成后直接制作Live，无需老板重复提出“生成Live”。老板当次明确要求静态图时按当次要求。

只对最终选中的图片生成Live，不将参考图、策划示意或整库照片批量转成发布资源。轻修先完成再生成，保留原始照片hash关系；不能通过Live转换绕过已发布素材去重。每张选定图分别保存配对JPG/MOV，保持发布顺序。封面取其关键照片，整组预览同时展示顺序、文案和动态效果。

原图裁切不适合、制作失败或动态验收未通过时，明确指出该张并修正或换图；不能静默跳过Live步骤、把MP4称为Live或声称已可发布。平台LIVE识别尚未验证时，预览明确标注待验证。

## 单张照片制作 Live Photo（已实现）

适用于用户提供的真实照片或明确选定的自家素材。先看原图，检查来源、画幅、主体位置和已发布去重。使用本目录 `scripts/make_live.py`，具体命令与传输说明见[使用说明：单图制作Live](使用说明.md#单图制作-live-photo)。不要再调用output内临时样例脚本。

当前效果是3秒、1080×1440、30fps的中心裁切推近：约1.05秒内从1.02倍推到1.11倍，然后停稳，附轻微平移，无声。它不生成湖水、烟气或人物的独立运动。横图及主体靠边的图先评估裁切；不适合则说明并换图，不能为凑效果截断重要商品。用户要其他运动方式时另实现并验证，不假称已经支持。

生成到当前项目 `制作内容/<日期>/<主题>_Live_vN/`，输入原图不改，已存在目录拒绝覆盖。输出配对的 `Fridge_Live.JPG`、`Fridge_Live.mov` 和MP4预览；技术报告与首尾检查图放该版本的 `验收/`。配对资源须一起保留，MP4不是Live Photo。Apple PhotoKit识别成功仅表示本机配对有效，不等于小红书已经认可。

生成后播放预览，查看首尾图及静态关键照片，验收主体裁切、黑边、清晰度和运动是否自然。图像生成的运动不能称现场实拍动态。向用户交付原图来源、效果说明和未验证边界；当前版本仍是候选，用户确认且账号/地点/素材核对后才能发布。原图已发布过的，做成Live仍遵守原图去重。

平台交付：先验证相册将JPG＋MOV识别为一个Live资源，再在目标客户端检查LIVE标识和播放。任何一步仅显示静态图或普通视频，记录实际结果，不声称Live发布成功。首次相册导入及对外操作遵循当次用户授权。

## 将Live配对文件导入Mac照片

用户实测：将JPG和MOV拖入Mac照片App会拆成静态图和视频，不能把这条路径写成自动合并保证。PhotoKit文件加载成功与相册中的photoLive类型验证是两项不同检查。

需要导入时，使用本目录 `scripts/build_live_importer.py` 构建Mac导入器（详见[使用说明](使用说明.md#导入mac照片为一个live项目)）。导入器通过同一个 `PHAssetCreationRequest` 添加 `.photo` 与 `.pairedVideo`，用户选择文件夹并点击导入后申请图库权限；成功后回读新项目的 `.photoLive` 类型。构建、配对检查不导入图库；未经当次授权不替用户点击导入。导入不删除先前误导入的两个项目，也不上传或发布。

同一配对标识已成功导入时检查本地回执，避免重复添加；写入成功但回读不确定时先检查图库，不盲目重试。导入回执仅存本机App偏好，不提交Git。手机接收后再验证LIVE，小红书识别仍独立验收。

手机端教学默认3:4竖图、主体拍大、边缘为Live裁切留余量。避免连续相似整柜封面；环境横图可后置，不为统一比例破坏内容。当前Live固定3:4，必须检查首尾裁切。
